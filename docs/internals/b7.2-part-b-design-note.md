# B7.2 Part B: supervision-tree declarations as AOT tree-shaking roots

Status: design finalized (this revision), not yet implemented. Two
sequential pieces, in strict order — do not start piece 2 before
piece 1 is landed, verified, and the empirical cross-check harness
(below) is real and running green.

## Confirmed finding that reframes this whole item (read this first)

Direct code reading, not inference: `tools/mkimage.ben`'s ONLY
stripping logic (lines ~134-172) strips a `defn`'s boxed bytecode body
**only when that function's NAME appears in `native-names.txt`** (i.e.
it got a native C kernel replacement) — a pure name match, nothing to
do with reachability. The `else` branch of that loop
(`(array/push kept f)`) keeps **every other top-level form
unconditionally**. `tools/callgraph.ben`'s `reachable-from`/`roots`/
`tainted` machinery is grepped-confirmed to have ZERO references
anywhere in `mkimage.ben`. **There is no tree-shaking anywhere in
this toolchain today.** `reachable`/`tainted` is purely advisory
within `callgraph.ben` itself, consumed only for (a) native-kernel
candidate selection and (b) diagnostic printing. Every `defn` in a
program ships in the final AOT image regardless of whether anything
calls it.

This means Part B is not "extend an existing gate" — it is "build a
gate that has never existed, with real correctness stakes; a false
positive (dropping something actually reachable through a path the
analysis missed) breaks the program, not just leaves it slower." The
design below treats that correctly: as a new safety-critical system,
not an extension of a system that already had to be safety-critical.

## Piece 1: whole-program dead-code elimination in `mkimage.ben` (general, NOT supervision-tree-specific — build and prove this first)

### The correctness design (read in full before writing a single line of stripping code)

1. **A deliberately more paranoid reachability computation than the
   existing `reachable-from`.** Do not reuse `callgraph.ben`'s
   analysis as-is for stripping decisions — it was tuned for a
   fail-soft consumer (miss a native-compile opportunity) and may
   contain unsoundness that was invisible because wrong answers there
   were harmless. Build a separate, explicitly named computation
   (e.g. `dce-reachable`) whose default is maximally conservative: the
   whole program is marked NOT SAFE TO STRIP ANYTHING if it contains
   even one instance of any of the following, enumerated exhaustively
   up front rather than discovered by trial and error:
   - A function value stored in a table/array/struct and invoked
     later through that container, rather than called directly by
     name at a static call site. **This is not a hypothetical edge
     case — it is exactly the shape `sup/child`'s own `entry`
     argument uses today**, and exactly the shape this whole feature
     needs to eventually treat as a well-defined, narrow exception
     (piece 2), never as a silently-assumed-safe default.
   - A function passed to a higher-order core function (`map`,
     `filter`, `each`, event/callback registration, anything that
     calls through a parameter rather than a literal name).
   - A function looked up via `resolve`/`dyn`/environment
     introspection, or any construct that resolves a callee by a
     runtime-computed symbol/string rather than a literal at compile
     time.
   - A function exported from the analyzed unit and potentially
     called by code outside it (a library, not a closed-world binary).
   - A function invoked only by the C host directly — `BENDER_CORE_REG`
     cfun registration, GC finalizer callbacks, FFI trampolines — none
     of which show up as an ordinary Bender-level call edge at all.
   - Any construct not on this list that the implementer is not 100%
     certain is statically resolvable. The default for "not sure" is
     always "taint everything," never "assume it's fine."
2. **An empirical cross-check harness, trusted independently of the
   analysis.** For any candidate "safe to strip" set the analysis
   produces, build TWO AOT binaries from the same source — one with
   that stripping applied, one without — and run the ENTIRE existing
   test corpus (every suite currently in `test/`, not a subset, plus
   ttfx's full effect battery at
   `/Users/pankajdoharey/Development/Projects/ML/ttfx`) against both,
   asserting byte-identical output. This is the same oracle-gate
   discipline already load-bearing everywhere else in this codebase's
   history (the `--pgo` byte-identical gate; every Stream-C phase's
   interpreter-vs-native diff) — here it is the actual safety net,
   not documentation of intent. No stripping decision is trusted on
   static analysis alone; it is trusted because this harness proved
   it on the real, full corpus.
3. **V1's baseline is allowed to strip nothing.** If a real program
   (ttfx, or this repo's own test corpus) contains any of the
   disqualifying patterns above anywhere — which is likely, given
   `proc/spawn` closures and ordinary higher-order Bender code — V1
   correctly strips zero functions. That is the honest, correct
   starting point, matching this whole engagement's established
   precedent (Phase 5 scoped to single-function closed-shape tables;
   every "honest finding, not forced" note throughout Streams A-C) —
   not a failure to report around.
4. **Hard build-time failure over silent wrong output.** If the
   conservative analysis cannot positively classify every construct in
   the program, the build must refuse to strip (fall back to keeping
   everything, the status quo today) rather than guess. A DCE build
   flag should almost certainly exist (opt-in, like `--native`/`--pgo`
   already are) so this is never silently on for existing build
   invocations.

### Required testing for piece 1
- The cross-check harness itself needs its own test: deliberately feed
  it a known-wrong "unreachable set" (one that actually IS reachable)
  and confirm the harness detects the resulting output divergence and
  fails loud — the harness's own correctness must be demonstrated
  before it's trusted to validate anything else.
- A positive case: a program with zero disqualifying dynamic patterns
  and at least one genuinely unused top-level function, confirming it
  gets stripped and the cross-check harness confirms identical
  behavior.
- A negative case: a program with exactly one disqualifying pattern
  (e.g. a function stored in a table and invoked later) confirming the
  WHOLE build correctly refuses to strip anything, not just the one
  ambiguous function.

## Piece 2: wire supervision-tree child declarations in as precise roots (only after piece 1 is real, tested, and committed)

Once `dce-reachable` + the cross-check harness exist and are proven,
add the FIRST narrow exception to the "function stored in a container"
taint rule: recognize a call to `sup/child` by resolved callee name,
and when its `entry` argument is a bare top-level function reference
at that exact call site (per `examples/supervisor.ben`'s own already
-documented contract — never a computed expression, reassigned local,
or inline `(fn ...)`), treat `entry`'s referent as reachable instead
of as an instance of the generic "stored-then-invoked" taint pattern.
Any `entry` argument that doesn't match this exact bare-reference shape
contributes no root and must NOT cause the whole build's conservative
fallback to trigger just because of it — it is simply treated as an
ordinary instance of the generic taint rule above (fail-open per
function, not fail-open for the whole build).

### Required testing for piece 2
- A fixture with a supervision tree declaring children plus at least
  one deliberately unreferenced top-level function; confirm the
  unreferenced one is actually dropped from the built binary (checked
  via `nm`/`strings` on the artifact, not just a diagnostic print
  line) and the cross-check harness confirms identical runtime
  behavior for everything that IS kept.
- A fixture where `entry` is NOT a bare reference (e.g. computed, or a
  local variable); confirm it contributes no root, the function it
  would have referenced still ships (conservatively kept, correct
  default), and the build does not spuriously fall back to
  stripping-nothing for the WHOLE program just because of this one
  ambiguous site.

## Standing warning, carried forward from Part A — do not repeat this class of regression

While building Part A (`examples/supervisor.ben`, commit
`42d19862`), a real bug was found and fixed: `teardown-child`'s quit
budget was a fixed 0.2s for every child, including nested supervisor
children. A nested supervisor's own graceful shutdown recursively
tears down its own children before it can reply, which routinely
exceeds a budget sized for a leaf worker. Losing that race caused an
ABRUPT `proc/kill` of the nested supervisor BEFORE it could tear down
its own children — orphaning them. The reproduced case was an
infinite-loop worker left alive forever, hanging the whole process on
exit. Fixed by giving supervisor-type children a 3.0s budget instead
of 0.2s (workers unaffected), still safely under `stop-tree`'s own
top-level 5.0s race.

**This exact class of bug — a timing budget sized for the simple case
silently failing once real recursion/depth is involved, with an
abrupt-teardown fallback that orphans what it was supposed to clean up
— must be explicitly checked for again in ANY future change to
`examples/supervisor.ben`, `tools/callgraph.ben`'s treatment of
supervision constructs, or anything related to process/fiber teardown
ordering in this codebase.** Any new nesting depth, new restart
pattern, or new teardown path introduced by Piece 1 or Piece 2 above
must include an explicit test exercising at least 2-3 levels of
nesting/recursion under time pressure (a tight, bounded test, not an
indefinite one) before being considered complete — the same way
`test/suite-supervisor.ben`'s test 5 now permanently guards the
original regression.
