# B7.2 Part B: supervision-tree declarations as AOT tree-shaking roots

Status: design note only, not implemented. Scoped down from a full
implementation after Part A (the runtime library,
`examples/supervisor.janet`, `test/suite-supervisor.janet`) landed
and was verified — per this project's own repeated precedent (Phase 5
scoped itself to single-function closed-shape tables rather than the
full whole-program design) of landing the honest, narrower, verified
piece over an unverified larger one, given the effort already spent
recovering Part A from two failed delegation attempts.

## The goal (restated from the session's design discussion)

`tools/callgraph.janet`'s `reachable-from` pass (search for `roots`
built from every top-level `thunk`) already does real whole-program
reachability analysis, but today its roots are maximally conservative
(every script body) and anything reaching a dynamic call site —
which `proc/spawn` with a runtime-computed target is — gets marked
`tainted` and exempted from pruning entirely (search for the `tainted`
fixpoint, backwards over call/contains predecessors from every
`dynsite`). The goal is to make a supervision tree's declared
children (via `sup/child`) statically visible to this pass, so they
become precise additional roots instead of relying on "everything is
reachable" by default.

`examples/supervisor.janet`'s own header already states the intended
contract precisely: the `entry` argument of `sup/child` must be a
bare, top-level, statically-referenced function VALUE at the call
site (never a computed expression, reassigned local, or inline `(fn
...)`); anything else stays correct at runtime but contributes no
root (fail-open — never a false root).

## What's confirmed, by direct reading, before any implementation attempt

1. `roots` (the `reachable-from` seed set) and `edges` (`"calls"`/
   `"contains"`/`"dynamic"` tuples) are both already-existing data
   structures in `tools/callgraph.janet`; the right implementation
   extends these, never invents a parallel mechanism — confirmed
   correct per the file's own established pattern across Phases 1-5.
2. `tools/callgraph.janet`'s existing `'call`-opcode resolution
   (search for where a callee's def id is resolved, e.g. the `cmap`/
   `tid` machinery used throughout Phases 1-5's native-eligibility
   checks) already proves "this call site's callee is exactly def
   id N" for ordinary calls. What it does NOT yet do — unconfirmed
   whether this is a small extension or a different mechanism
   entirely — is resolve "this call's ARGUMENT (not its callee) is a
   bare reference to a known top-level function," which is the
   bytecode pattern `(sup/child :name worker-fn :permanent)` actually
   produces (an `ldu`-or-similar load of `worker-fn` as a VALUE,
   pushed as an argument to the `sup/child` call, not itself a call
   site). This needs direct investigation of what bytecode op loads a
   bare top-level function reference used as a value (likely `ldu`,
   based on Phase 1-3's commentary that `ldu` loads are "dead in
   emitted code: static calls go direct by name" — meaning the
   EXISTING infra treats a function-value load as inert data, which
   is exactly backwards from what Part B needs: it needs to make that
   load's referent count as reachable, not continue ignoring it).

## The real open question that must be resolved before implementation (not yet investigated)

**Does `reachable`/`tainted` from this pass actually control what
code is physically included in the final AOT image, or only what
`tools/callgraph.janet` reports/decides for NATIVE kernel eligibility
and diagnostic printing?** This is the single most important
unknown. If `tools/mkimage.janet`'s actual code-stripping logic (what
gets compiled into the final binary at all, as opposed to what gets a
fast native kernel vs. stays boxed/interpreted) does NOT consult
`reachable`/`tainted` today, then Part B's mechanism — however
correctly implemented inside `callgraph.janet` — would NOT actually
achieve "tree shaking" in the sense of a smaller final binary; it
would only affect which functions are considered for native
compilation, which is a real but different and smaller win than what
was asked for. This must be confirmed by reading `tools/mkimage.janet`
in full (not partially, as prior sessions did under time pressure)
before writing a single line of the actual mechanism, because it
determines whether this is "extend an existing pass" (if mkimage
already consumes `reachable`) or "wire a previously-advisory-only
analysis into the actual stripping decision for the first time" (a
materially bigger, riskier change if not).

## Recommended next step (not started)

1. **Investigate first, as a standalone step**: read `tools/mkimage.janet`
   end to end to answer the open question above. This alone may take
   real effort and should be its own bounded task before any code is
   written.
2. **If `reachable` already gates physical inclusion**: implement the
   argument-resolution extension described above (recognize `sup/child`
   calls by resolved callee def id, resolve the `entry` argument via
   whatever bare-top-level-function-reference mechanism the
   investigation above identifies, inject it as an additional root
   exactly where `thunk` roots are seeded today) and verify with a
   fixture declaring 2-3 children plus at least one deliberately
   unreferenced top-level function, confirming the unreferenced one is
   excluded from the final binary (not just "reported as
   unreachable" in diagnostic print output — the actual binary must
   be smaller/missing that symbol, checked e.g. via `nm`/`strings` on
   the built artifact, not just the `reach` print line).
3. **If `reachable` does NOT already gate physical inclusion**: this
   becomes a larger, two-part task (first wire `reachable` into
   `mkimage.janet`'s actual stripping decision for ordinary code in
   general, verified not to regress anything currently included by
   the conservative "every thunk is a root" default, THEN add the
   supervision-tree-specific root injection on top) and should be
   re-scoped and re-planned as such, likely split across two
   dispatches rather than attempted as one.
4. Either way, the fail-open negative case (an unresolvable `entry`
   expression contributes no root but never causes a crash or false
   unreachability for code otherwise proven reachable through ordinary
   call edges) must be a first-class, explicitly tested property from
   the start, not an afterthought — same discipline as every
   soundness-sensitive phase in this project's history.
