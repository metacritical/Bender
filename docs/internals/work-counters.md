# Deterministic work counters (AOT/native)

## Purpose and headline

The headline is **interpreted bytecode instructions retired per rendered frame**, with the frame count held fixed by `--dump-frames --max-frames N` (never infer a frame count from variable-duration `--bench`). The adjacent native-operations-per-frame and VM-boundary-exits-per-frame numbers are separate dimensions. A native operation and a bytecode dispatch are **not equivalent units**: do not add them into a percentage of time or claim that `interpreted / (interpreted + native)` is CPU occupancy. This work vector replaces noisy cross-build wall time for *attribution and direction*, not for a final speedup claim. A change can reduce counts yet run slower because of instruction cost, cache locality, branch prediction, allocations, or binary layout; the reverse is possible too. Report elapsed-time measurements separately and with their measured uncertainty.

## Invocation

Build the compiler with `make NATIVE_EXECUTORS=1`, set `JANET_NATIVE_EXECUTORS=1` while **emitting** the AOT image, and compile a telemetry-enabled native image (`--aot ... --native`, **not `--release`**). An already-built image with linked native descriptors and a native-enabled runtime does **not** require that environment variable at execution; it is not a runtime toggle. A normal image supports:

```sh
JANET_NO_PROFILE=1 ./effect \
  --work-profile /tmp/effect-work.json decrypt --dump-frames \
  --max-frames 400 --input-file ../ruby-port/logo.txt --seed 42 \
  > /tmp/effect-frames.out
```

`--work-profile -` writes JSON to stderr; a file path keeps stdout exclusively for the application. The switch and its destination are removed before Janet sees `:args`; no application output is added. An absent destination, a plain image, or telemetry-disabled release fails explicitly. Set `JANET_NO_PROFILE=1` **also for the uninstrumented control**, or the profile machinery changes continuation eligibility (an observed zero-chains/89,849-refusals trap). Every run emits a short stderr summary and JSON with `schema`, `deterministic`, `advisory_gc`, `top_native_ops`, and `top_vm_exits`. The top lists each contain up to ten *nonzero* definitions in descending metric order, ties by numeric manifest ID. Each row carries ID, name, entries, ops, VM exits and chained calls. Compare JSON with `cmp` over five repeated runs of the exact same executable, argv, seed and input; separately compare stdout bytes against a run without the switch.

## Inventory and exact counting sites

| Counter | Counting site and interpretation |
|---|---|
| Interpreted dispatches (new) | `src/core/vm.c` `VM_START` and `vm_next` in both computed-goto and switch forms: increment immediately before an interpreter opcode dispatch, including first dispatch after re-entry. `vm_native` may run native instructions before the tick; those instructions are not falsely counted as VM dispatches. |
| Native ops, entries, backedges, fallbacks, VM boundary exits and chained edges (existing) | `tools/loop-executor.janet` emits `NX_TICK/ENTRY/EDGE/FALLBACK/VMEXIT/CONT` for each Tier-B descriptor. `tools/callgraph.janet` exposes `executor-stats(id)` tuple `[entries, backedges, fallbacks, ops, vmexits, continuations]`; `native-executors.txt` maps ID to name. `NX_TICK` is a generated work tick, **not a sound retired-per-PC count**: some ticks precede later guards or polls, and fused operations cover multiple original PCs. Never use it as the numerator of the numeric-opportunity stop gate. `NX_VMEXIT` is a particular generated boundary site; global VM exits also include other native-to-VM exits, so their totals need not agree. |
| Native-to-VM exits and exit-opcode histogram (existing) | `src/core/vm.c` `vm_native` increments `native_vm_exits` and `native_exit_opcodes[*pc & 0xFF]` on trampoline `JANET_NATIVE_VM`; `executor-exit-stat(opcode)` and global tuple index 4 expose them. Native entry/re-entry proxy is the sum of per-definition `entries`: entries include resumes and chaining, not just exits' one-to-one inverse. |
| Interpreted Janet-function calls, native chains, refusal, native returns (existing) | `src/core/vm.c` JOP_CALL and `janet_native_call_enter`/`janet_native_ret_pop`; `executor-global-stats()` indices 9,6,7,8 respectively; per-definition `conts` attributes chains to caller. `interpreted_calls + chained_calls` is the call-edge conservation check in the tested continuation workload; interpreter calls exclude C-function calls and tail calls. |
| Native kernel invocations (existing, separate tier) | `tools/callgraph.janet` generates per-kernel `*_telemetry_calls` (plus guard failures) or dispatcher variants/fallbacks and `atexit` stderr lines `native-telemetry id=...`; these are wrapper calls, not Tier-B `NX_TICK` operations. The JSON currently covers Tier-B executors, **not** kernel call totals; parse these separate lines when kernel activity matters. |
| Attach attempts/attached/ambiguous/no-match (existing) | `src/core/bytecode.c` `janet_native_try_attach` and `janet_native_stat`, global tuple indices 0–3. These describe registration/attachment, not executed work; `available N` alone proves no live execution. |
| GC-object allocations and requested bytes (new advisory) | `src/core/gc.c` `janet_gcalloc`, after successful allocation; requested bytes omit slab internal fragmentation and external buffer storage/`janet_gcpressure`. `src/core/gc.c` `janet_gc_barrier` counts calls even if immediate values return before any remembered-edge change. |
| GC cycles (new advisory) | Actual major, global minor, fiber minor and process minor collection entries after the suspend gate; delegated fallbacks count only the global minor. `JANET_GC_COUNT` historically counts cycles only when separately built with that diagnostic define and prints on major entry, not as a final aggregate. |

All new increments are under `JANET_NATIVE_EXECUTORS && JANET_NATIVE_TELEMETRY`; the default for telemetry-enabled native images is 1. `--release` passes `-DJANET_NATIVE_TELEMETRY=0` for generated executors and the reporter; it is **not** a counter probe. Runtime increments have per-dispatch/per-native-op/per-allocation/per-barrier costs, and change generated code layout; the report adds a single exit-time O(number of definitions × 10) top-N selection and file write, with no Janet allocations or hash traversal. The existing per-definition TLS counters are read on the main thread; activity on additional OS threads is not aggregated.

## Determinism contract and limits

The `deterministic` vector and top lists are ordered by explicit manifest IDs, not address or hash iteration. For a fixed build, input, seed, environment, frame count and single-threaded scheduling, integer counts and JSON bytes should repeat exactly. Prove this **per workload**; byte-identical visual output alone is insufficient. Native ops and interpreter dispatches can still change if scheduling or a GC-triggered path changes; concurrent workloads, host-dependent I/O, or nondeterministic hash iteration violate the preconditions. The `advisory_gc` object is deliberately **excluded from the deterministic core** because allocation/collection timing and interleavings can alter its totals; it does not promise identical bytes across machines or threads. A complete JSON file can be bit-identical in a specific controlled run, but this is empirical evidence, not a universal guarantee.

Use positive nonzero `top_native_ops`/`native_entries` to prove live executors, a nonzero `chained_calls` to prove selected continuation edges, `JANET_NO_PROFILE=1`, and exact program-byte parity before comparing vectors. Compare each component separately, always quote seed/frame count and exact binary revision. Historical cross-build wall timing on this host falsely found a 4.04% binarypath change between two builds of identical generated C; do not translate count deltas into speedup percentages.

## Profile representativeness: continuation v1 versus narrowed v2

A pinned, telemetry-enabled comparison used pre-continuation `66a5cf9a`, always-attempt v1 `3db27d20`, and narrowed v2 `e03ba5ed`, with the same ttfx source, seed 42, logo input, `--dump-frames --max-frames 400`, `JANET_NO_PROFILE=1` on **each runtime command**, and `JANET_EXECUTOR_LEAF_MIN_CALLS=500`. v1 and v2 were trained on decrypt; v2 also used `JANET_EXECUTOR_EDGE_MIN_CALLS=500`. Each historical image linked its *own* pinned runtime plus a disposable measurement-only interpreter-dispatch overlay (the pre image also needed a JOP_CALL counter); all four effect dumps remained byte-identical across revisions. Never substitute inferred pre-call counts: the actual pre-image counter read 653,830 / 2,408,002 / 534,828 / 2,272,883 respectively. The decrypt-trained images each selected 96 executors and retired identical native-operation counts per effect.

|---|---:|---:|---:|---:|
| decrypt | 18,672,489 / 18,431,435 / 18,432,093 | 90,034 / 89,380 | 654 | 658 / 658 |
| rings | 113,188,121 / 113,125,945 / 113,127,919 | 19,344 / 17,378 | 1,966 | 1,974 / 1,974 |

For each row `pre interpreted_calls = v1 interpreted_calls + v1 chained_calls = v2 interpreted_calls + v2 chained_calls` was independently measured, not assumed. The five decrypt-selected PCs were `ctx-new-scene` PCs 2→`ctx-anim` and 8→`scene-new`, `ctx-scene` PC 2→`ctx-anim`, `ctx-add-frame` PC 2→`ctx-scene`, and `ctx-apply-gradient` PC 44→`ctx-add-frame`. v1's binarypath top-N attributes exactly 30,846 chains to `travel-complete?`, absent from those five; binarypath is therefore worse under the decrypt-trained narrowing, not because a runtime guard began refusing a previously accepted edge. v1 attempts at every non-terminal call PC, whereas v2 attempts only at selected PCs: their refusal totals have different denominators and are **not** comparable success rates.

As a representativeness check, a separate binarypath-trained pinned v2 selected ten PCs, including `travel-complete?` PC 20→`ctx-anim` (31,002 profiled calls) and the motion/path edge `ctx-coord-on-line` PC 3→`geom-lerp-point` (129,151 profiled calls). On binarypath its live chains rose from the decrypt-trained v2's 45,385 to 216,823, and interpreted dispatches fell from 65,131,718 to 59,849,603 with identical output. **This is not an isolated continuation A/B:** binarypath training also changed the selected executor set from 96 to 107 and native operations from 47,782,078 to 53,148,727; do not credit the whole dispatch reduction to chaining or infer a time speedup. The result supports the operational rule that profile-narrowed emission needs representative training across intended effects; single-effect training can make an untrained effect do *more* interpreter work than unnarrowed v1. See `native-continuation-design.md` for the selection/threshold contract.

### Capstone: decrypt + binarypath + rings auto-PGO at threshold 500

At pinned v2 `e03ba5ed`, build a profile-free `--native --no-auto-pgo` training image, keeping the **same output basename** and a fresh dedicated `XDG_CACHE_HOME`. Run that image with each effect and the fixed 400-frame arguments above: the first decrypt run writes the base `.jdn`, then `JANET_AUTO_PGO=1` scoped to the binarypath and rings runs writes two `.jdn.run-*.jdn` sidecars, each with a replayable `.workload`. Do **not** set `JANET_NO_PROFILE` on these *training* runs. Rebuild at the same output path with `--native --pgo-auto`, `JANET_EXECUTOR_LEAF_MIN_CALLS=500` and `JANET_EXECUTOR_EDGE_MIN_CALLS=500`. The v2 builder reported **3 auto profiles / 3 distinct workloads**, generated an independent interpreter oracle for each, merged them with `tools/profile-merge.janet`, passed all three parity gates, and published three gateable records. The joined profile contained `:calledges`; `native-continuations.txt` selected **13** PCs, including the prior five, `travel-complete?` PC 20→`ctx-anim`, `ctx-coord-on-line` PC 3→`geom-lerp-point`, and `rings-set-disperse-path` PC 24→`randrange`. No lower-threshold build was needed: the missing named edges were already selected at 500.

All rows below use the same seed 42, logo input and 400 frames; every image has positive live native entries/operations/chains and byte-identical application stdout on each effect. Historical pinned v1/v2 dispatch instrumentation and the legacy pre-call retrofit are **disposable measurement overlays**, not native reports from the original commits. The pre image did **not** originally expose `interpreted_calls`: its original value is **unavailable**, not zero; the separate retrofit directly measured the pre counts stated above. For each effect, the *directly measured* pre JOP_CALL count equals interpreted calls plus chains in **all three** profiled images: 653,830 decrypt, 2,408,002 rings, 534,828 beams, 2,272,883 binarypath. The merged image recovers at least v1's chain count on rings, beams and binarypath, and all but 259 decrypt chains; it does **not** keep v2's near-zero refusal tally on every workload (397 decrypt, 4,003 beams, 792 binarypath). A selected PC is only an invitation to try: the guard revalidates the live callee and safely falls back on refusal. v1 attempted at every non-terminal call PC while v2 attempted only at selected PCs, so refusal **rates** and raw difference across versions have incompatible exposure denominators. Within v2, these are actual attempt-failure counts, not a zero-cost guarantee. With the enlarged executor set, VM exits even *increase* for rings and binarypath while interpreter dispatches decrease; do not sum unlike counter units or claim speedup. **Operational choice:** representative multi-workload selection solves the missing-edge *coverage* at this threshold, but neither universal near-zero guard waste nor an equal-executor-set cross-image advantage was shown. Gate any shipping image with effect-specific selection manifests, parity, executor/native-op census, call conservation, and work vectors; use a separately named build for a threshold change.

### Same-binary binarypath control: continuation enabled versus disabled

The cross-image −5,282,115 dispatches for binarypath-trained versus decrypt-trained v2 is **confounded** by leaf-tier selection (107 versus 96 executors), so it is **not** a continuation-only result. Instead, execute each *already-built pinned v2 image itself* twice on binarypath, seed 42, logo input, 400 frames, inline `JANET_NO_PROFILE=1` in both runs; disable continuation in only the OFF invocation with `JANET_NATIVE_NO_CONTINUATION=1`. No compiler, generated C, executor set, binary or input changes inside either pair. Both ON/OFF pairs have byte-identical stdout (SHA256 `c96d7773edbe47f3ae029dd3b0d751a3438150c604396544f9b871b6a2ef3c16`). The image-specific positive counters verify the native tier is live; values are integer work, **not timing**.

|---|---|---:|---:|---:|---:|---:|---:|
| decrypt-trained v2, 96 executors | OFF | 0 | 2,272,883 | 65,264,779 | 1,115,740 | 47,782,078 | 1,159,567 |
| decrypt-trained v2, 96 executors | ON | 45,385 | 2,227,498 | 65,131,718 | 1,049,976 | 47,782,078 | 1,159,567 |
| binarypath-trained v2, 107 executors | OFF | 0 | 2,272,883 | 60,302,302 | 2,042,165 | 53,148,727 | 2,086,659 |
| binarypath-trained v2, 107 executors | ON | 216,823 | 2,056,060 | 59,849,603 | 1,674,933 | 53,148,727 | 2,086,659 |

**Within each unchanged image**, ON saves 45,385 calls / 133,061 dispatches / 65,764 VM exits for decrypt training, versus 216,823 calls / 452,699 dispatches / 367,232 VM exits for binarypath training. In each pair, `OFF interpreted_calls = ON interpreted_calls + ON chained_calls = 2,272,883` exactly; native operations, native entries and native-boundary exits remain invariant. The toggle establishes that chaining itself removes those measured calls/dispatches/exits *within each image*. The binarypath-trained image obtains 171,438 more chains and a 319,638 larger within-image dispatch reduction than decrypt-trained v2; this **comparison of paired effects remains conditional on their differing 96/107 executor sets** and is not a pure edge-selection effect size independent of leaf-tier changes. `JANET_EXECUTOR_LEAF_MIN_CALLS=500` is itself workload-sensitive under a single-effect profile: the same source selects 96 versus 107 executors.

The selected PCs explain the mechanism more directly than cross-build totals. Decrypt training chose five scene/animation *construction* edges listed above, while binarypath training selected `travel-complete?` PC 20→`ctx-anim` (31,002 profile calls) and `ctx-coord-on-line` PC 3→`geom-lerp-point` (129,151): this latter is **exactly the motion/path call edge predicted in continuation design §5**. The design's prediction was borne out by binarypath selection; decrypt was simply not representative training for that motion edge. The merged decrypt + binarypath + rings image has already selected both sets (13 PCs) and covered the missing chains; it still needs per-effect guard/work gating before shipping because some merged-image refusals are nonzero (up to 4,003 beams), and no elapsed-time speedup is inferred.
