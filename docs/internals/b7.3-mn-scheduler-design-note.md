# B7.3: M:N scheduler core / resident-proc migration — scoped design note

Status: investigation only, nothing implemented. Written directly
after two failed subagent attempts at this investigation; findings
below are grounded in direct code reading.

## Q1: Is a live, already-running proc ever movable between lanes?

**No.** Confirmed by reading every lane primitive in `src/core/proc.c`:
- `proc/lane-pin` (`proc.c:221`) pins the *calling OS thread* to a CPU
  core (affinity), unrelated to moving a Bender-level proc anywhere.
- `proc/lanes-policy` (`proc.c:538`) has a `:steal` mode, but its own
  docstring is explicit: it rebalances **where NEW spawns land**
  ("spawns overflow to a global queue... idle lanes pull from it") —
  it never touches a proc that has already started running on a lane.
- The resident lane dispatcher's own comment (`proc.c:231-237`) lists
  exactly three messages a lane understands: `:spawn` (create a new
  local proc), `:deliver` (route a message to an existing local
  proc's mailbox), `:stop` (shut the lane down). There is no `:move`/
  `:migrate` message or anything resembling one anywhere in this
  dispatch set.

Placement is decided once, at spawn time, by whichever policy is
active (round-robin or steal-for-overflow), and is permanent after
that.

## Q2: How real is this gap — and a related finding worth flagging on its own

Attempted to build a numeric fixture (spawn a mix of short- and
long-lived procs round-robin across 4 lanes, then inspect per-lane
occupancy to show imbalance). **Could not complete this as originally
asked**, for a concrete reason: `proc/lanes-stats` (`proc.c:574`)
exposes exactly two counters, both about the `:steal` overflow queue
(`:overflow-pushed`/`:overflow-pulled`) — there is no public API
anywhere that reports **current per-lane occupancy** (how many procs
are resident on lane N right now). This is itself a real, concrete
finding: the system cannot even **observe** load imbalance across
lanes today, which is a prerequisite for any rebalancing mechanism
(migration or otherwise) — you cannot correct what you cannot see.
This should be scoped as part of the same future work, not assumed to
already exist.

Given that, the realistic scenario demonstrating the gap is simpler
than a numeric reproduction: any program whose actual per-proc
workload is not uniform (some procs do much more work than others)
and is spawned round-robin will end up with uneven real load across
lanes, with (a) no visibility into that imbalance and (b) no
mechanism to correct it even if it were visible. This is a real,
plausible limitation for an actor-heavy workload (e.g. an MMO/game
backend, the stated motivating use case for this whole engagement)
where actor lifetimes and work intensity are naturally non-uniform.

## Q3: What would migration actually require, mechanically?

Checked directly: each lane is a **separate OS thread running its own
VM with its own slab state** (confirmed via
`docs/internals/per-proc-gc-independence.md`, written this same
session during B4's GC work: "every fiber/proc allocates from one
VM-global slab state... Collections are scoped sweeps over a SHARED
heap" — shared *within* a VM, but each lane/worker VM has its own).
A fiber's actual C stack (`fiber->data`, confirmed in `gc.c` around
line 541) is allocated from its home VM's heap. Moving a live proc to
a different lane means moving that allocation (and everything it
transitively references) to a **different VM's heap entirely** — not
a pointer reassignment, a real cross-heap transplant.

This is NOT cheap, and is NOT separable from the broader per-proc GC
independence effort already scoped (as a separate, not-yet-built
epic) in `docs/internals/per-proc-gc-independence.md`. That note's own
staged plan (per-owner slab arenas → per-arena accounting → private
minors → shared/private edges → majors/teardown) is close to a
prerequisite for migration to even be contemplated safely: you cannot
move a proc's allocations between VMs cleanly until each proc's
allocations are already somewhat decoupled from "whichever VM's slab
state happened to serve this request," which is exactly what that
design note is working toward for a different reason (GC
independence, not migration).

**This contradicts the original roadmap's framing** (B7.3 described as
an independent, parallel track, gated only on B5.1's lanes crash fix,
now resolved). It is not actually independent of B4's GC-independence
work — it is a likely downstream consumer of it.

## Recommended first increment

Before anything resembling migration: add a per-lane occupancy
counter to `proc/lanes-stats` (or a new `proc/lane-occupancy`
primitive) so load imbalance becomes observable at all. This is small,
has no correctness risk (pure instrumentation, no behavior change),
and is a real prerequisite for any future rebalancing work — whether
that ends up being migration or something simpler (e.g. a
spawn-time-only heuristic informed by current occupancy, which would
NOT need the heavy cross-heap transplant mechanism Q3 describes, and
could land well before true migration is ever attempted). Actual
proc migration itself should stay explicitly gated on
`per-proc-gc-independence.md`'s own staged plan reaching at least its
first milestone (per-owner slab arenas), not attempted before that.
